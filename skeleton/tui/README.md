A prototype generated by [proto-pilot](https://github.com/skyrowlabs/proto-pilot).

```bash
make install     # into a virtualenv you already activated

```

## One process, one file

There is no server, no port, no container and no Postgres. The whole
application is `python -m app.main` and the database is a SQLite file beside
it, which is why this tree has no `compose.yml`, no `Dockerfile` and no health
check — there is nothing to wait for and nothing to orphan.

`APP_DB` overrides where that file goes. The test suite sets it to a temporary
directory, so running the tests never touches the database you were looking at.

## What is generated and what is not

`app/models.py`, `app/screens.py`, `app/seed.py`, `app/widgets.py`,
`app/app.tcss` and `tests/test_smoke.py` carry a GENERATED banner — they are
rewritten whole by `proto add`. Everything else (`app/main.py`, `app/db.py`,
`app/base.py`, `tests/conftest.py`, `tests/screen.py`, `tests/test_boots.py`)
is the fixed skeleton and is identical in every proto-pilot terminal app.

Editing a generated file is fine — it is your repo now — but the next
`proto add` will overwrite it.

`tests/screen.py` is worth knowing about before you write a test of your own:
it is how a test reads what the app is showing, and reading a `Static` any
other way is the single most common way a passing app fails its own suite.

## Data

There are no migrations. `Base.metadata.create_all()` runs when the app mounts
and `app/seed.py` refills an empty database, so `make clean && make run` is a
full reset.
